# Confirming Discovered Roles

## Overview

`discovering-user-roles` proposes; this skill **confirms and generates**. It
takes `discovered-roles.json`'s `roles[]` (and, on the weak-signal path,
`candidates[]`) and runs it through a **3-round human-in-the-loop
confirmation** — roles, then credentials, then scope — following the
frontier-in-rounds pattern in
[hitl-rounds.md](../bootstrapping-qa-config/references/hitl-rounds.md). Once
all three rounds settle, this skill **deterministically WRITES** two
artifacts via a script — never hand-authored JSON in prose:

1. `.qa/config.json`'s `personas[]` — one `{ id, role, plane, auth }` per
   confirmed role, **replacing** any existing `personas` block wholesale.
2. `.qa/authz-matrix.json` — one row per protected entity, carrying its
   FK-ownership chain and which confirmed personas may see it, **replacing**
   any prior file wholesale.

**Regenerate, not reconcile (Decision 5).** Every time this skill runs to
completion it produces a fresh, complete `personas[]` and a fresh, complete
authz matrix from the CURRENT confirmed set — it never diffs against, merges
into, or partially updates a prior confirmation's leftovers. A dropped role
from a prior run simply does not appear; there is no stale entry to clean up
because nothing survives except what this run's rounds confirmed.

## Vocabulary (CONTEXT.md-aligned + hitl-rounds.md)

- **round / frontier / recompute** — see
  [hitl-rounds.md](../bootstrapping-qa-config/references/hitl-rounds.md);
  this skill is that pattern's canonical consumer.
- **persona** — this phase populates only the **role** axis of
  `persona = role × lens` (the lens axis — skeptical-auditor/first-time-user/
  a11y-user — is later-phase scope, added additively on top of what this
  skill writes; never regenerated by it).
- **owning chain** — the ordered FK hops from a protected entity back to the
  record that actually owns it (e.g. `submission → team_id → team →
  hackathon_id → hackathon`), used to say which hop a given role's isolation
  boundary sits at. Comes from `discovering-user-roles`' contextual-role scan
  and this skill's own Round 3 chain-following (see Step 4).

## When to Use

- Immediately after `discovering-user-roles` writes
  `.qa/runs/<run-id>/discovered-roles.json`, before `generating-qa-checklist`
  runs its Step 6 cross-role expansion (that step reads `personas[]` /
  `.qa/authz-matrix.json`, not the raw discovery proposal).
- Whenever `discovered-roles.json` is regenerated (RBAC source changed) —
  re-run this skill too; it never trusts a stale prior confirmation.
- Even on the `signal: weak` degrade path, still run all 3 rounds if
  `roles[]` or `candidates[]` is non-empty — a single weak candidate still
  deserves a numbered confirm/drop decision, not a silent skip. Only skip
  entirely when both arrays are empty (nothing to confirm).

## Engine (`frontier.js`)

Every round below is this skill driving
[`frontier.js`](scripts/frontier.js) — the dependency-free, pure, tested
topological round engine (`tests/frontier/run.sh`, `PASS=6`). frontier.js
does no I/O, no prompting, and no fact discovery; this skill supplies the
tree, the facts, and the human interaction, and calls exactly its four
exports:

- **Tree shape:** `{ nodes: [{ id, prereqs, default }] }` — one node per
  decision. `prereqs` is hitl-rounds.md's `dependsOn` under its concrete
  name; `default` is what `recommendedDefault()` reads (hitl-rounds.md's
  `recommendedDefault` key). frontier.js is agnostic to node granularity —
  this skill instantiates one node **per `{role}` / `{role,cred}` /
  `{role,entity}` decision** (`role:admin`, `cred:admin`, `scope:admin`,
  ...), not one aggregate node per round.
- **`computeFrontier(tree, settled)` → `{ frontier, deferred, settledIds }`.**
  `frontier` = every unsettled node whose `prereqs` are all keys of
  `settled`; everything else unsettled is `deferred`. Call this once per
  round to know what to render next.
- **`recommendedDefault(tree, id)`** is a static read of that node's
  `default` field — frontier.js never computes a recommendation itself.
  Where a step below says a downstream recommendation is "re-derived using
  the new account's actual data," that derivation is THIS skill re-running
  its own discovery/citation logic and overwriting the node's `default` in
  place before the next `recommendedDefault()` call — the engine only
  echoes back whatever `default` currently holds.
- **`applyAnswers(tree, settled, answers)` → next `settled`.** Confirms and
  first-time answers just add `answers` into `settled`. **Unsettle-on-edit:**
  if an `id` was ALREADY in `settled` and the new answer differs from the
  old one, every transitive dependent of `id` (found by walking `prereqs`
  chains) is deleted from `settled`, so it falls out of `settledIds` and
  re-enters the frontier on the next `computeFrontier` call. In this
  skill's strict forward Round 1 → 2 → 3 flow that branch rarely fires — a
  downstream node usually isn't settled yet when its upstream is first
  answered, so there is nothing to unsettle. It exists for the REVISION
  case: a human reopening an already-answered round after a later round has
  already settled (e.g. "actually, drop evaluator" after Round 3 already
  ran) — reapplying that answer through `applyAnswers` automatically clears
  every settled downstream id for a clean re-render, with no separate
  revision code path needed.
- **Dropping has no dedicated status in frontier.js — model it by
  omission.** A dropped id is simply never added to `settled`; its
  dependents' `prereqs` are then never fully satisfied, so they sit in
  `deferred` forever and are never rendered — this is how "removed from the
  tree entirely" (below) cashes out against the real engine, without
  actually deleting anything from `tree.nodes`. **Caveat:** the dropped
  node's own `id` still has no unmet `prereqs`, so it would reappear in
  `frontier` on every later `computeFrontier` call unless this skill tracks
  it. Maintain a session-local `decided` set (every id the human has
  confirmed, edited, OR dropped) alongside `settled`, and always render
  `computeFrontier(tree, settled).frontier` **minus** `decided` — never the
  raw `frontier` array.
- **`budgetExceeded(roundsCompleted, 3)`** — call after any round the host
  can't complete interactively (Step 4's "Never block"). Once it returns
  true, auto-accept `recommendedDefault` for every remaining frontier id
  across the current and any later round in one pass, tag each
  `"assumption": true`, and proceed straight to Step 5.
- **Downstream consumer:**
  [`write-persona-config.sh`](scripts/write-persona-config.sh) is what
  actually enforces two of these rounds' invariants — unique persona `id`s
  and `roleScope` values restricted to `owns|read-scoped|none` — by
  rejecting the write outright if Round 1 or Round 3 ever produced a
  duplicate id or an out-of-enum scope. Rounds 1 and 3 below must stay
  honest about those constraints; the script is the enforcement backstop,
  not this skill's own bookkeeping.

## The Process

### Step 1 — Load the proposal and build the decision tree

- [ ] Read `.qa/runs/<run-id>/discovered-roles.json`. Treat `roles[]` as the
      confirmable set; if `signal: "weak"`, also include `candidates[]`,
      each flagged low-confidence in its citation.
- [ ] Per hitl-rounds.md Step 1: build the FULL 3-round decision tree before
      rendering anything — one `role:<name>` node per discovered role (no
      dependencies), one `cred:<name>` node per role depending on its
      `role:<name>`, one `scope:<name>` node per role depending on its
      `cred:<name>`. Facts (enum cases, seeded fixture rows, FK columns) are
      already sitting in `discovered-roles.json` plus a fresh grep for
      fixture/seed data backing each role's `auth` field — never ask the
      human "what roles does your app have."
- [ ] Build this as `frontier.js`'s literal tree: one object
      `{ nodes: [...] }`, each node `{ id: "role:<name>", prereqs: [],
      default: "keep — include, test as this role" }`, `{ id: "cred:<name>",
      prereqs: ["role:<name>"], default: <Round 2 recommendation> }`, `{ id:
      "scope:<name>", prereqs: ["cred:<name>"], default: <Round 3
      recommendation> }` — see [Engine](#engine-frontierjs) above for the
      field-name mapping to hitl-rounds.md's `dependsOn`/`recommendedDefault`.

### Step 2 — Round 1: Roles

- [ ] Render the frontier (every `role:<name>` node — no dependencies yet)
      as **one numbered list**, each item showing its `source` citation
      (verbatim from `discovered-roles.json`) and a recommended default of
      **"keep — include, test as this role."**
- [ ] A role flagged `unused: true` or `drift` in `discovered-roles.json`'s
      `driftNotes[]` gets a recommended default of **"keep, but flag
      low-confidence"** instead of a plain keep — surface the drift/unused
      note inline so the human sees why before deciding.
- [ ] Ask the human, in one prompt (`AskUserQuestion` in Claude Code, plain
      numbered text elsewhere): confirm the full set, edit any item's
      inclusion, or drop any item. Wait for the complete answer batch.
- [ ] **Recompute:** call `applyAnswers(tree, settled, answers)` with only
      the CONFIRMED/edited items — a dropped role is never added to
      `answers`/`settled` (see Engine above). Add every id from this round,
      confirmed or dropped, into the `decided` set. Then
      `computeFrontier(tree, settled)`: any `cred:<name>`/`scope:<name>`
      node whose role was dropped has an unsatisfiable `prereqs` entry and
      stays in `deferred` forever, so it is never rendered or written to
      the artifacts. Round 2's frontier (minus `decided`) = one
      `cred:<name>` node per surviving role.

### Step 3 — Round 2: Credentials (unblocked once roles settle)

- [ ] For each role confirmed in Round 1, render a recommended default
      **auth method**, derived from `discovered-roles.json`'s `auth` field
      for that role:
      - If `auth` already names a seeded-credential convention (e.g.
        `qa.{role}@<host>`), recommend **"seeded-credential login"**, citing
        the seeder.
      - If `auth` names a `storageState` path, recommend **"use that
        storageState capture."**
      - If `auth` is `"unknown"` (a common, honest answer for contextual
        roles — see `discovering-user-roles` Step 4), recommend **"capture a
        fresh storageState by logging in as this role's account"** and cite
        why no seeded credential was found.
- [ ] **Never guess or print a password.** Recommendations and the human's
      edits may only reference login conventions, fixture usernames, or
      storageState paths — a literal password value must never appear in
      the round's rendering, the confirmed answer, or the written artifact,
      even if source code has one in plaintext (mirror
      `discovering-user-roles` Step 4's rule exactly).
- [ ] The human may edit an item to point at a **different** seeded account
      for the same role (e.g. swapping an empty fixture for one that
      actually owns data) or to switch methods entirely (seeded → captured
      storageState). Wait for the full batch.
- [ ] **Recompute:** apply Round 2's answers with `applyAnswers`, and add
      every Round 2 id to `decided`. For the edited item, this skill (not
      frontier.js) re-derives the not-yet-rendered `scope:<name>` node's
      `default` from the new account's actual data and overwrites it on the
      tree before Round 3 renders — sibling roles' `scope:<name>` nodes are
      untouched. (`applyAnswers`'s unsettle-on-edit branch only matters if a
      credential is edited AFTER its scope node already settled — a
      revision, not this forward pass; see Engine above.) A dropped Round-1
      role has no Round-2 entry to begin with — its `cred:<name>` node's
      `prereqs` were never satisfied (Step 2).
- [ ] **Persona-identity capture (gap #6, downstream of this round).** A
      confirmed persona's `auth` here is only a login CONVENTION — it does
      not, by itself, prove which identity a later Verify-phase session is
      actually acting as. When Verify logs in as this persona (this skill
      does not do that itself), it must probe a read-only `whoami`/profile
      endpoint — or decode the subject out of the `storageState` the login
      produced — and record it via `record-evidence.sh identity --persona
      <id> --subject <captured-subject> --method <whoami|storageState>`; if
      the app exposes no such probe, `--method none` instead of skipping the
      call. `qa-verify` then binds that capture to every persona-scoped
      `human-action`/`cross-tenant`/`cross-role-fk-chain` `pass` for this
      persona. An OVERRIDE to fail requires operator ground truth: only when
      `personas[].expectedSubject` is configured for that persona AND the
      captured subject doesn't match it. Without a configured
      `expectedSubject`, comparing a bare persona `id` to an opaque captured
      subject (a numeric account id, a short hash, a JWT `sub` claim) is not
      confident enough to hard-fail on its own — a non-matching subject
      degrades confidence to `low` instead (best-effort substring match
      against `id` still verifies). An absent/unverifiable identity
      (`method:none` or no `identity.json`) also degrades rather than
      blocking (spec §5.5). Operators who want a genuine impersonation to
      hard-fail, not just degrade, must configure `expectedSubject` for that
      persona. Note this expectation nowhere in the written artifacts — it
      is Verify-phase doctrine, not a Round 1–3 decision.

### Step 4 — Round 3: Scope

- [ ] For each role with a settled Round-2 credential, walk the codebase's
      FK-ownership chain(s) touching that role's account (policy checks,
      scoped-query `where`/`->whereHas` clauses, pivot lookups) — same
      chain-following `discovering-user-roles` uses for contextual roles,
      generalized: follow every hop back to the ultimate owning record, not
      just one `tenant_id`-shaped column.
- [ ] Render the frontier as one numbered list: per role, its recommended
      scope classification — **`owns`** (no scope filter found; role can
      read/write the entity outright), **`read-scoped`** (a filter ties
      visibility to this role's own assigned rows — cite the filter), or
      **`none`** (no code path reaches the entity for this role at all) —
      one line per `{role, entity}` pair the scan found evidence for.
- [ ] Ask the human to confirm, edit, or add a `{role, entity}` classification
      per item. Wait for the full batch.
- [ ] **Recompute:** nothing downstream of Round 3 exists in this skill
      (it's the last round) — an edit here only affects what Step 5 writes
      into the authz matrix, no further round to invalidate.
- [ ] **Never block.** Per hitl-rounds.md's round-budget rule (3–5 rounds;
      this flow IS 3 rounds, so the budget is exactly used up by design): if
      a host environment can't complete all 3 rounds interactively (e.g. a
      `/loop`-driven autonomous run), call `budgetExceeded(roundsCompleted,
      3)`; once it returns true, auto-accept `recommendedDefault` for every
      remaining frontier id (this round and any later one) in a single
      pass, tag each accepted item `"assumption": true` with reason `"round
      budget exhausted"` in the artifacts below, and proceed — never leave
      `personas[]`/the authz matrix unwritten because a host didn't
      respond.

### Step 5 — Generate the artifacts (deterministic, scripted)

Never hand-author the JSON. Materialize the confirmed rounds as two small
JSON files, then call the writer script:

- [ ] Write `.qa/runs/<run-id>/confirmed-personas.json` — a JSON array, one
      object per role that survived Round 1, using Round 2's confirmed
      credential as `auth`:

  ```json
  [
    { "id": "admin", "role": "admin", "plane": "global",
      "auth": "qa.admin@<host> (seeded credential; password via named constant, not printed)" },
    { "id": "evaluator", "role": "evaluator", "plane": "global",
      "auth": "qa.evaluator2@<host> (seeded credential — swapped in Round 2, owns assigned submissions)" }
  ]
  ```

  `id` is the persona's stable identifier (equal to `role` unless Round 2
  bound two distinct accounts to the same role, in which case disambiguate,
  e.g. `evaluator-2`). `plane` is copied from `discovered-roles.json`
  (`global` or `contextual`).

- [ ] Write `.qa/runs/<run-id>/confirmed-authz-matrix.json` — a JSON array,
      one row per entity the Round 3 scan found evidence for:

  **Authz-matrix row schema (concrete):**

  ```json
  {
    "entity": "submission",
    "owningChain": ["team_id", "hackathon_id"],
    "roleScope": {
      "team-member": "owns",
      "evaluator": "read-scoped",
      "jury": "read-scoped",
      "admin": "owns",
      "user": "none"
    }
  }
  ```

  - `entity` — the protected model/table name (string).
  - `owningChain` — ordered array of FK hop column names from the entity
    back to its ultimate owning record. A single-tenant `tenant_id` column
    is the chain-length-1 special case (`["tenant_id"]`); most real apps
    have length ≥2 (e.g. `innovation`'s `submission` has no `tenant_id` at
    all — ownership is `team_id → team → hackathon_id → hackathon`).
  - `roleScope` — object keyed by **persona id** (must match an id in
    `confirmed-personas.json` — the writer script rejects unknown keys),
    value one of `"owns" | "read-scoped" | "none"`.
  - This is the artifact `generating-qa-checklist`'s cross-role heuristic
    and any downstream cross-role negative test read to know which
    entity/role pairs must show absence — see that skill's Step 6.

- [ ] Call the writer script to validate and write both real artifacts in
      one deterministic step:

  ```
  bash skills/confirming-discovered-roles/scripts/write-persona-config.sh \
    --personas-file .qa/runs/<run-id>/confirmed-personas.json \
    --matrix-file   .qa/runs/<run-id>/confirmed-authz-matrix.json \
    --config .qa/config.json --matrix-out .qa/authz-matrix.json
  ```

  The script (a) validates every persona has `id`/`role`/`plane`/`auth` with
  `plane` in `global|contextual`; (b) validates every matrix row has
  `entity`/`owningChain` (non-empty array)/`roleScope` (object) and that
  every `roleScope` key names a persona id that actually survived
  confirmation — rejecting the write outright (non-zero exit, nothing
  touched) if a row references a persona nobody confirmed; (c) on success,
  **replaces** `.qa/config.json`'s `personas` key wholesale and **replaces**
  `.qa/authz-matrix.json` wholesale. It requires `.qa/config.json` to
  already exist (from `bootstrapping-qa-config`) and needs EITHER `jq` OR
  `python3` — same dependency convention as the plugin's other bundled
  scripts.

### Step 6 — Hand off

- [ ] Report the written counts (`N personas`, `M authz-matrix rows`) and
      note any `"assumption": true` entries from a budget-exhausted round.
- [ ] Point `generating-qa-checklist` at the fresh `.qa/config.json`
      `personas[]` and `.qa/authz-matrix.json` for its cross-role expansion
      and role-sensitive tagging.

## Guardrails

- **Regenerate, not reconcile.** Both artifacts are fully replaced every
  successful run — no partial merge, no leftover entries from a role that
  was dropped this time.
- **Facts are discovered before rounds render; only decisions are asked.**
  Never phrase a round as "what roles/credentials/scope does your app
  have" — that is `discovering-user-roles`' and this skill's own
  static-analysis job, done before Step 2/3/4 render anything.
- **Never guess or print a password.** `auth` fields are conventions and
  citations only, in every round and in the written artifact.
- **Never hand-author `.qa/config.json` or `.qa/authz-matrix.json`.** Always
  go through `write-persona-config.sh`; a hand-edited trailing comma or a
  dangling `roleScope` reference is exactly the bug class the script's
  validation exists to prevent.
- **Never block indefinitely.** Past the 3-round budget, log assumptions
  and proceed — an unattended `/loop` run must still produce a usable
  config.

## Mini-Evals (given → outcome)

**Eval 1 — Full 3-round flow on a spatie/innovation-style app, with an edit
in Round 1 and Round 2 (grounded in `hitl-rounds.md`'s worked example)**
*Given* `discovered-roles.json` lists 5 global roles
(`super-admin/admin/evaluator/jury/user` from `UserType`) plus a
`team-member` contextual candidate from the `team_members.role` pivot, each
with a source citation and an `auth` convention (`qa.{role}@<host>` seeded
logins for the global roles; `auth: unknown` for `team-member`).
*Outcome:* Round 1 renders all 6 as a numbered list; the human drops
`team-member` ("covered by `user`'s own team-scoped actions already").
Recompute removes `team-member`'s not-yet-rendered `cred`/`scope` nodes.
Round 2 renders 5 credential recommendations; the human edits `evaluator`'s
seeded account from `evaluator@example.test` (no assigned submissions) to
`evaluator2@example.test` (has 3). Recompute regenerates only
`scope:evaluator`'s recommendation, scoped to `evaluator2`'s actual assigned
rows; the other 4 scope nodes are untouched. Round 3 renders 5
`{role, entity}` scope rows including
`{ entity: "submission", owningChain: ["team_id","hackathon_id"],
roleScope: {"evaluator": "read-scoped", "admin": "owns", ...} }`; the human
confirms all 5 as recommended. Step 5 writes
`.qa/runs/<run-id>/confirmed-personas.json` (5 entries, `evaluator`'s `auth`
reflecting the Round-2 edit) and `confirmed-authz-matrix.json` (rows keyed
only by the 5 surviving persona ids), then calls
`write-persona-config.sh`, which replaces `.qa/config.json`'s `personas[]`
(5 entries, no `team-member`) and writes `.qa/authz-matrix.json` — both
files regenerated wholesale, matching the frontier-recompute trail exactly.

**Eval 2 — Degrade/anonymous case (weak signal, near-empty proposal)**
*Given* `discovered-roles.json` has `signal: "weak"`, `roles: [{"name":
"anonymous", ...}]`, and one `candidates[]` entry (`owner-check (literal
email)`, `plane: "unknown"`, `auth: "unknown"`).
*Outcome:* this skill still runs all 3 rounds rather than skipping outright
(both arrays are non-empty). Round 1 lists both `anonymous` and the
low-confidence candidate, each citing its source, with the candidate's
recommended default flagged "keep, but flag low-confidence" per Step 2's
drift/unused rule (a weak-signal candidate is treated the same way as a
`driftNotes`-flagged role). The human confirms both. Round 2 recommends
`auth: unknown → capture a fresh storageState` for the candidate (no seeded
credential exists) and `auth: none needed` for `anonymous`. Round 3 finds no
FK-ownership evidence for either (a single-user app has nothing to scope),
so it emits a single `owningChain: []`-free note rather than a fabricated
row — Step 5 still writes a valid (2-persona) `confirmed-personas.json`, but
`confirmed-authz-matrix.json` is written as an empty array `[]` (not
omitted — the writer script's non-empty-array validation applies only when
a matrix is expected; here Step 4 explicitly records "no protected entities
found to scope" so the empty result is a deliberate, cited outcome, not a
silent gap). `generating-qa-checklist`'s cross-role row for this project
correctly defers with reason "single-role app — no second role/tenant to
probe," per that skill's own existing rule.

**Eval 3 — All-defaults-accepted pass-through**
*Given* `discovered-roles.json` proposes 3 clean, strong-signal global roles
with corroborated seeders and no drift/unused flags.
*Outcome:* per hitl-rounds.md's pass-through case, the human accepts every
recommended default in all 3 rounds with zero edits and zero drops. Each
round still renders exactly once, in order — Round 1 (3 roles), Round 2 (3
seeded-credential recommendations, unchanged), Round 3 (3 scope
classifications, unchanged) — but recompute finds nothing to regenerate
after any of them (no edited/dropped ids), so no round is re-shown. Step 5
writes `confirmed-personas.json`/`confirmed-authz-matrix.json` exactly
matching the original recommendations, and `write-persona-config.sh`
succeeds on the first call with no validation failures, since every
`roleScope` key trivially matches one of the 3 confirmed persona ids.
