# ADR-0012 — Per-role cost containment, most-privileged ordering, and relational cross-role negative tests

## Status

Accepted (2026-08-31). Part of the accuracy overhaul ([docs/plans/2026-08-30-qa-accuracy-persona-overhaul.md](../plans/2026-08-30-qa-accuracy-persona-overhaul.md), Settled Decision 6), implemented in Phase 2 ([docs/plans/2026-08-31-phase2-coverage-roles.md](../plans/2026-08-31-phase2-coverage-roles.md), Workstream 2B, Tasks 2B.2–2B.5).

Status convention note (see ADR-0011 for the full statement): Accepted here means the decision is the one actively being implemented this phase, not that every task that exercises it has already landed.

## Context

ADR-0011 settles that QA runs as discovered roles. Left open: if every criterion re-ran once per discovered role, an 8-row edge-case catalog against, say, 3 write-bearing surfaces and 5 discovered personas produces well over a hundred criteria — under ADR-0003's sequential-by-default execution that is a combinatorial cost the plugin cannot pay for criteria that have nothing to do with role at all (most functional/computed-logic checks behave identically regardless of who is logged in). At the same time, the entire *point* of adding roles is to catch bugs only visible when comparing across roles — one persona seeing another's data — and `innovation`, the real multi-role project this phase measures against, has no single `tenant_id` column to check for that; ownership is a multi-hop relational chain (`submission → team_id → team → hackathon_id → hackathon`). A flat "assert a `tenant_id` mismatch" heuristic fails open on this shape by construction. Finally, once any criterion can run more than once (once per persona), the existing checkpoint scheme — keyed by `criterion_id` alone — cannot tell two personas' runs of the same criterion apart, which silently reads a different persona's untested case as already covered on resume.

## Decision

Four settled decisions, together:

1. **Only `role-sensitive` criteria and authz negative tests multiply per persona; shared criteria run ONCE, as the most-privileged role** (master plan Decision 6). A criterion is tagged `role-sensitive` when its outcome plausibly differs by who is logged in (permission-gated actions, role-scoped list/detail views, anything the authz matrix marks as anything other than uniformly `owns` across all roles); everything else is "shared" and is not re-walked per persona. This is what keeps the 8-row edge-case catalog × N surfaces × up to ~8 discovered personas from becoming the full cross-product — a **criteria budget** (default 60, overridable via `.qa/config.json`'s `criteriaBudget`) is enforced in `generating-qa-checklist` after the catalog walk (including persona multiplication of role-sensitive rows); exceeding it stops the generator before finalizing the checklist and presents a numbered, prioritized confirm-or-trim prompt (write-bearing + role-sensitive + previously-missed-bug-class rows prioritized first, read-only/cosmetic edge rows last) rather than silently emitting everything.

   **Explicit role-privilege total order**, required because the source enum is not a clean permission ladder: for `innovation`'s `UserType` (`super-admin/admin/evaluator/user/jury`), the order used **only** to pick which single role runs a shared criterion is:

   ```
   super-admin > admin > evaluator ≈ jury > user
   ```

   This is stated explicitly as a **selection convenience, not a claim of a real permission lattice** — `evaluator` and `jury` are lateral, scope-limited roles (each sees only their own assigned submissions; neither is a superset of the other, hence `≈`) rather than strict supersets of `user`. The ordering exists solely so "run once as the most-privileged role" has a deterministic answer; it does **not** exempt `evaluator`-vs-`jury` isolation from being tested as an explicit cross-role pair regardless of where they sit in this ordering — two lateral roles can still leak into each other's data, and that must still be tested. Contextual team roles (e.g. a `team_members.role` pivot) are scoped **under their team**: privilege ordering is compared only within the same contextual scope (one team's roles against each other), never across teams, since a role in team A has no privilege relationship to a role in team B — that relationship is cross-role-fk-chain isolation (Decision 2 below), not ordering. A project with no discoverable ordering hint (no obvious "admin"-shaped naming) defaults to declaring every role tied and requires a Round-1 (ADR-0011) human confirmation of the order before it is used.

2. **Cross-role negative tests assert absence against relational FK-ownership CHAINS, not a single tenant-id column.** "Persona B must not see persona A's owned entity" is generalized from a single hardcoded `tenant_id`-equality check to walking an arbitrary ownership chain — the authz-matrix's `owningChain` array (e.g. `submission → team_id → team → hackathon_id → hackathon`) — and asserting absence at whichever hop the persona under test does not own. The flat-column case (a genuine single `tenant_id` filter) is kept as the chain-length-1 special case under the `cross-tenant: true` tag, so existing single-tenant projects are unaffected; the new general case is tagged `cross-role-fk-chain: true` and carries the specific chain being asserted, read from the authz-matrix artifact ADR-0011 produces (`{ entity, owningChain: [...], roleScope: { <roleId>: "owns"|"read-scoped"|"none" } }`). **A `pass` on a cross-role-fk-chain criterion requires a `probe` bake showing absence** — an authenticated fetch/read-back as persona B that confirms persona A's entity is not returned at the correct hop, per the evidence-gate content requirements ADR-0010 already enforces for the `probe` kind. A UI that merely fails to render a link to the entity is not evidence of absence; the probe must show the backend itself withholds it.

3. **Checkpoint and evidence records are keyed by the pair `(criterion_id, persona_id)`, not `criterion_id` alone.** Once a role-sensitive criterion runs once per persona, a `criterion_id`-only key would let a `pass` checkpointed while QA-ing as persona A read back as "already done" on resume when the orchestrator is actually about to run the same criterion ID as persona B — silently skipping real per-persona verification (the resume-path false-green failure mode). `checkpoint.sh` and `record-evidence.sh` take an optional `--persona <persona-id>`; when present, the upsert/lookup/resume/list predicate matches on both fields, and the evidence artifact path is namespaced per persona so artifacts cannot collide. Omitting `--persona` is exact back-compat with today's `criterion_id`-only behavior (persona stored/matched as empty), so shared criteria and pre-Phase-2 runs are unaffected. Acceptance is concrete and testable: checkpointing `(C7, admin)` as `pass` and then resuming must still require the orchestrator to execute `(C7, evaluator)` — it must not be reported as already done.

4. **The authz check for a given project is MEASURED, not asserted qualitatively.** Because the synthetic fixture is single-user (documented Phase 0 scope boundary) and cannot host a multi-role isolation test, role/authz recall is measured against the real multi-role project (`innovation`): a minimal, revertible authz defect (e.g. temporarily dropping the `team_id`/`hackathon_id` scope filter on one endpoint the authz matrix already marks `read-scoped` for the persona under test) is seeded on a disposable local checkout, the new cross-role-fk-chain criterion must catch it (`fail`, `suspectedLayer` pointing at the layer holding the missing filter, evidence citing the leaked entity by ID), and once reverted the same criterion must stay silent (`pass`, `probe` evidence of absence) — a recall/precision pair, using the harness's existing attribution machinery, not prose.

## Consequences

- Bounds run cost: the vast majority of criteria (shared, non-role-sensitive) run exactly once regardless of how many roles are discovered; only the criteria that could plausibly differ by role, and dedicated authz negative tests, pay the per-persona multiplier — and even that multiplier is capped by the criteria budget with a human-reviewable trim proposal rather than silently exploding.
- Cross-role isolation testing works on relationally-modeled applications with no `tenant_id` column at all, which is the actual shape of `innovation` and, per the master plan, presumably other target projects — the flat-column heuristic remains available as the degenerate case rather than being replaced outright.
- Resume correctness is preserved under role multiplication: a long run interrupted mid-persona-sweep resumes into exactly the personas/criteria pairs not yet done, never masking an untested persona as covered.
- The most-privileged ordering is documented as a deterministic tie-breaker, not a security model — nothing downstream may read `super-admin > admin > evaluator ≈ jury > user` as evidence that, say, `evaluator` really can do everything `user` can. That the ordering does not exempt lateral-role pairs from isolation testing is stated to prevent exactly that misreading.
- Evidence-gate content requirements (ADR-0010) apply unchanged to the `probe` kind used by cross-role-fk-chain criteria — this decision does not weaken or special-case what counts as valid probe evidence, it only adds a new criterion shape (chain-hop absence) that must satisfy the same gate.

## Alternatives considered

- **Run every criterion once per discovered role** (no shared/role-sensitive split): rejected — an N-role project multiplies the entire checklist by N even for criteria whose outcome cannot differ by role (e.g. "does the amount field format to two decimals"), which is pure token/time cost for zero additional recall and would make the criteria-budget guard trigger on nearly every multi-role project.
- **Single flat `tenant_id`-equality isolation check, kept as the only cross-role test**: rejected as the sole mechanism — it fails open (asserts nothing, or asserts against a column that doesn't exist) on any relationally-modeled app like `innovation`, which is exactly the shape the master plan requires this phase to be measured against. Kept only as the chain-length-1 special case for genuinely flat-tenant projects.
- **Leave checkpoint keyed by `criterion_id` alone and rely on the orchestrator to track personas in its own working state**: rejected — run state belongs on disk per ADR-0002, not in the agent's transient reasoning; anything not in the persisted checkpoint record is exactly the kind of state a context-compaction or resumed session loses, reintroducing the false-green resume risk this decision closes.
- **Treat the source role enum's declaration order as the privilege ladder**: rejected — confirmed against `innovation`'s actual `UserType` enum, declaration order does not correspond to privilege, and `evaluator`/`jury` are lateral rather than ordered; an explicit, documented, human-confirmable ordering (with a stated tie-break default) is required instead of inferring one mechanically.
